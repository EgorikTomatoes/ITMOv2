## 1. СЕРВЕРНЫЕ ТЕСТЫ

**Файл:** `tests/alerts.test.js`

### 1.1. «Создаёт активное уведомление» — ✅ PASSED
**Действие:** создаётся уведомление BTC для пользователя u1 с условием above и ценой 60 000.
**Проверяется:**
- уведомление принадлежит пользователю u1;
- выбран символ BTC;
- начальный статус равен active;
- используется тип notificationType = in_app;
- уведомление действительно добавлено в хранилище.

### 1.2. «Проверяет условия above и below с достижением порога» — ✅ PASSED
Проверяется логика сравнения рыночной и целевой цены:
- above с ценой, равной порогу, возвращает true;
- above ниже порога возвращает false;
- below с ценой, равной порогу, возвращает true;
- below выше порога возвращает false.

### 1.3. «Срабатывает при пересечении верхнего порога и сохраняет цену» — ✅ PASSED
**Действие:** цена BTC повышается с 50 000 до 56 000 при пороге 55 000.
**Проверяется:**

- сохраняется фактическая цена срабатывания 56 000;

## 2. КЛИЕНТСКИЕ ТЕСТЫ

**Файл:** `frontend/src/pages/PriceAlerts.test.jsx`
**Инструменты:** Vitest, jsdom, Testing Library и user-event.

Модуль services/api подменяется тестовыми функциями. Ответы имеют тот же формат, что и настоящее API. Тесты проверяют видимый результат действий пользователя, а не внутреннее наличие React-компонентов.

### 2.1. «Показывает загрузку, а затем понятное пустое состояние» — ✅ PASSED
**Сценарий:**
- запрос списка остаётся в состоянии ожидания;
- на экране отображается status «Загружаем уведомления»;
- сервер возвращает пустой массив;
- появляется текст «Здесь пока нет уведомлений»;
- кнопка «Создать уведомление» доступна пользователю.

### 2.2. «Открывает и закрывает диалог с клавиатуры» — ✅ PASSED
**Сценарий:**
- пользователь открывает форму создания;
- фокус автоматически устанавливается на кнопку закрытия;
- пользователь нажимает Escape;
- диалог исчезает из интерфейса.

### 2.3. «Проверяет обязательное поле и некорректную цену» — ✅ PASSED
Проверяется два случая:
- при пустом поле появляется сообщение «Укажите целевую цену», а API не вызывается;
- при цене -1 появляется сообщение «Цена должна быть положительным числом»;
- поле получает доступный признак aria-invalid = true.

### 2.4. «Показывает ошибку API и позволяет повторить отправку» — ✅ PASSED
**Сценарий:**
- первая отправка возвращает ошибку «Сервис временно недоступен»;
- сообщение отображается через role=alert;
- поле цены снова становится доступным и сохраняет введённое значение;
- повторная отправка завершается успешно;
- диалог закрывается;
- API был вызван ровно два раза: неудачная попытка и осознанный повтор.

### 2.5. «Не создаёт второй запрос во время ожидания ответа» — ✅ PASSED
**Сценарий:**
- API намеренно отвечает с задержкой;
- после первой отправки кнопка меняется на «Создаём…» и блокируется;
- повторное нажатие на кнопку не создаёт новый запрос;
- количество вызовов createAlert остаётся равным одному;
- после получения ответа диалог закрывается.

Этот тест подтверждает защиту от двойного клика и повторного Enter во время ожидания.

### 2.6. «Проходит основной сценарий от ввода данных до результата в интерфейсе» — ✅ PASSED
Полный пользовательский сценарий:
- пользователь открывает форму;
- выбирает BTC;
- выбирает условие «Цена выше»;
- вводит цену 75 000;
- нажимает «Создать»;
- API получает payload { symbol: BTC, condition: above, targetPrice: 75000 };
- диалог закрывается;
- в интерфейсе появляется цена $75,000 и статус «Активно»;
- показывается сообщение «Ценовое уведомление создано».

### 2.7. «Показывает ошибку загрузки и восстанавливается после повтора» — ✅ PASSED
**Сценарий:**
- первый запрос списка завершается ошибкой «Нет связи с API»;
- пользователь видит доступное сообщение об ошибке;
- пользователь нажимает «Повторить»;
- второй запрос проходит успешно;
- интерфейс переходит в корректное пустое состояние.


## 3. ДИЗАЙН-ТЕСТЫ

**Файл:** `frontend/e2e/price-alerts.design.spec.js`

**Инструменты:** Playwright и настоящий Chromium.

**Эталонные изображения:** `frontend/e2e/__screenshots__/`.

Ответы `/api/market`, `/api/users`, `/api/notifications` и `/api/alerts` перехватываются фиксированными тестовыми данными. Поэтому скриншоты не зависят от содержимого локальной базы, времени ответа backend или состояния сети.

### 3.1. «Desktop соответствует утверждённому визуальному эталону» — ✅ PASSED
**Условия:** viewport 1440×900, тёмная цветовая схема, русская локаль, отключённые анимации.

**Проверяется:**
- заголовок страницы и счётчик двух активных уведомлений видимы;
- отрисованы строки BTC и ETH с фиксированными ценами и статусами;
- полный снимок страницы совпадает с `price-alerts-desktop.png`;
- допустимая доля отличающихся пикселей не превышает 1%.

Тест обнаруживает случайные изменения расположения блоков, размеров, цветов, типографики, таблицы, навигации и отступов на desktop.

### 3.2. «Mobile использует карточки и соответствует визуальному эталону» — ✅ PASSED
**Условия:** viewport 390×844.

**Проверяется:**
- desktop-таблица скрыта;
- вместо неё присутствуют ровно две мобильные карточки;
- кнопка создания, фильтры, цены, статусы и действия остаются видимыми;
- полный снимок совпадает с `price-alerts-mobile.png` при допуске не более 1% отличающихся пикселей.

Тест подтверждает не только CSS-breakpoint, но и реальный результат адаптивной вёрстки в браузере.

### 3.3. «Ключевые размеры, цвета и фокус совпадают с дизайн-токенами» — ✅ PASSED
**Проверяется:**
- высота кнопки «Создать уведомление» равна 44 px;
- фон основной кнопки соответствует lime-токену темы NOVA;
- высота счётчика «2 активных» равна 32 px;
- при клавиатурном фокусе рамка имеет толщину 3 px;
- цвет рамки равен `#b8f43d`.

Первый запуск этого теста выявил, что стиль daisyUI перекрывал проектное правило и оставлял рамку толщиной 2 px. Приоритет правила в `frontend/src/index.css` исправлен; повторный запуск подтвердил толщину 3 px.
