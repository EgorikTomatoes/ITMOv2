# Tree of Thoughts

- Решение, для которого нужны альтернативы: метод аудита учебного PR и experiment.md
- Критерии выбора: доказательность (QA-1), покрытие требований SEC-1/API-1/REL-1/OUT-1/OBS-1/SCOPE-1, независимость ветвей анализа, воспроизводимость

## Запрос

Негативный аудит PR и experiment.md методом нескольких независимых ветвей анализа (A–F). Источники: @practices/practice_01/TRAINING_PR.diff, @practices/practice_01/project_management.md, @practices/practice_01/CASE.md. Цель — доказательно показать, почему PR может быть некорректным.

## Внешне описанные альтернативы

| Альтернатива | Плюсы | Минусы | Оценка по критериям |
|---|---|---|---|
| A. Многоветвевой негативный аудит | Широкое покрытие, независимые взгляды, выявляет конфликты | Требует дисциплины по QA-1, может быть объёмным | Соответствует QA-1, покрывает SEC/API/REL/OUT/OBS, воспроизводим |
| B. Классический код-ревью одним треком | Быстрее, привычно | Пропускает несоответствия в артефактах и зависимостях | Недостаточно доказательств, узкое покрытие |
| C. Линт/статический анализ | Автоматизируемо | Не покрывает продуктовые требования и планы | Низкая доказательность по QA-1 |

## Выбор

- Выбранная альтернатива: A. Многоветвевой негативный аудит
- Почему: удовлетворяет QA-1, покрывает требования и артефакты, позволяет зафиксировать независимые противоречия
- Как проверим: для каждой проблемы укажем место, проблему, доказательство, последствия, критичность; ссылки на строки diff/плана/правил

## Отчёт по веткам (A–F)

### Ветка A — Требования

- Что должно быть по правилам CASE.md: SEC-1, API-1 (20 000 символов → 413), REL-1 (timeout 10s и контролируемая ошибка), OUT-1 (summary/risks/checks ≤3), SCOPE-1, QA-1, OBS-1.
- Реализовано в PR (TRAINING_PR.diff): POST /api/reviews с телом dict, делегирование в ReviewService.review; ответ {"comment": str}. Нет валидации поля diff, лимита длины, редактирования секретов, таймаута/обработки ошибок, структуры OUT-1, наблюдаемости.
- Отсутствует: API-1, SEC-1, REL-1, OUT-1, OBS-1; SCOPE-1 соблюдён.
- Частичная реализация: только каркас эндпоинта и делегирование к LLM; требований к контракту/устойчивости нет.
- Неподтверждённые требования: никакие целевые требования из плана (инкременты 1–3) не подтверждены кодом.

### Ветка B — Логика

- Зависимости: `from app.dependencies import review_service` (TRAINING_PR.diff app/api.py:30–31) — в diff не показана реализация зависимости, риск ImportError.
- Порядок инкрементов: project_management.md (стр. 7–9) требует сначала контракт/валидацию (422/413), затем безопасность/timeout, затем OUT-1/OBS-1; PR нарушает порядок, добавляя эндпоинт без инкремента 1.
- Причинно-следственные связи: отсутствие валидации → KeyError/500 при пустом теле; отсутствие лимита → риск перегруза LLM; отсутствие таймаута → зависания/500.
- Согласованность результатов: заявленные результаты инкрементов не прослеживаются в реализации.
- Невозможные/циклические зависимости: явных циклов нет; однако внедрение OUT-1 без инкремента 1 приведёт к ломающему изменению API.

### Ветка C — Проверки

- На каждый заявленный результат из плана нет проверок в коде: нет схемы/422/413, нет таймаута/обработки, нет нормализации OUT-1, нет логов.
- Граничные случаи не покрыты: отсутствие diff, длина 20 001, таймаут LLM.
- Несоответствие проверок заявленному поведению: OpenAPI/контракт не обеспечивает required `diff`.
- Заявлений «проверено» в PR нет; в project_management.md заявлена «корректность Mermaid Gantt», что конфликтует с находкой ниже.

### Ветка D — Конфликты

- Между PR и experiment.md: experiment.md (этот файл) был пустым — не может подтверждать соответствие; конфликт с требованием иметь воспроизводимый артефакт.
- Между зависимостями и Gantt/планом: план утверждает корректность Gantt, но есть риск синтаксической ошибки в строке с двоеточием в названии задачи (см. ниже в финальном списке).
- Между задачей и проверкой: план обещает обновлённый OpenAPI, но PR не вводит Pydantic-схем, следовательно required-поле `diff` не зафиксировано.
- Между заявленным результатом и реализацией: OUT-1 vs {"comment"}.

### Ветка E — Артефакты

- Mermaid Gantt: строка `LLM: безопасность и timeout :a3, after a2, 2d` (project_management.md:21) содержит двоеточие в названии и двоеточие перед id — потенциальный синтаксический риск.
- Даты: ориентировочные; противоречий не выявлено.
- Названия и ссылки: файлы и ссылки существуют (TRAINING_PR.diff, CASE.md), однако `app/` как каталог в репозитории отсутствует (учебный diff, не применён).
- Тесты/документация: описаны в .md, но в PR отсутствуют реальные тесты/схемы.

### Ветка F — Интеграция

- Несовместимые изменения интерфейса: сейчас ответ {"comment"}; переход на OUT-1 будет ломающим для клиентов.
- Отсутствующие зависимости: `app.dependencies.review_service` может отсутствовать, что приведёт к ImportError.
- Несогласованные интерфейсы: использование `dict[str, str]` требует Python ≥3.9 (целевой runtime не зафиксирован в CONTEXT.md — «открытый вопрос»).
- Конфликты компонентов: без лимита длины весь diff попадает в prompt → риск переполнения контекста LLM.

## Финальный отбор (сводный список проблем)

Ниже перечислены уникальные проблемы. Для каждой указаны: место; проблема; доказательство; последствия; критичность.

1) Место: TRAINING_PR.diff app/api.py:35–38; project_management.md:7
   Проблема: Нет валидации входа и обработки отсутствующего поля `diff` (ожидается 422).
   Доказательство: `return review_service.review(payload["diff"])` — прямой доступ по ключу; план (стр. 7) — «отсутствие diff → 422; лимит 20 000 → 413».
   Последствия: KeyError и 500 при пустом теле; нарушение API-1/Инкремента 1; ухудшение DX/надёжности.
   Критичность: Высокая.

2) Место: TRAINING_PR.diff app/api.py:35–38; CASE.md:65; project_management.md:7
   Проблема: Нет ограничения длины diff 20 000 символов и возврата 413 (API-1).
   Доказательство: В коде отсутствуют проверки длины; CASE.md (стр. 65) и план (стр. 7) требуют 413 при превышении.
   Последствия: Перегруз LLM, рост задержки/стоимости, нестабильность.
   Критичность: Высокая.

3) Место: TRAINING_PR.diff app/review_service.py:19–22; CASE.md:64
   Проблема: Нет редактирования/маскирования секретов перед отправкой в LLM (SEC-1).
   Доказательство: `prompt = f"...\n{diff}"` и прямой вызов `self.llm.generate(prompt)`; CASE.md (стр. 64) требует удалять токены/пароли/ключи.
   Последствия: Риск утечки секретов во внешний провайдер.
   Критичность: Высокая.

4) Место: TRAINING_PR.diff app/review_service.py:21; CASE.md:66
   Проблема: Нет таймаута 10s и контролируемой обработки ошибок LLM (REL-1).
   Доказательство: Прямой вызов `self.llm.generate` без таймаута/try-except; CASE.md (стр. 66) — требование REL-1.
   Последствия: Зависания, 500 при сбоях LLM; снижение SLO.
   Критичность: Высокая.

5) Место: TRAINING_PR.diff app/review_service.py:22; CASE.md:67–70; project_management.md:9
   Проблема: Ответ не соответствует OUT-1 — возвращается `{\"comment\": str}` вместо `{summary, risks≤3[file,line,evidence,risk], checks}`.
   Доказательство: `return {"comment": answer}`; правила OUT-1 в CASE.md; в плане (стр. 9) ожидается результат по OUT-1.
   Последствия: Невозможность автоматической обработки; несоответствие целевому контракту.
   Критичность: Средняя/Высокая.

6) Место: Весь PR; CASE.md:70; project_management.md:9
   Проблема: Отсутствует наблюдаемость (OBS-1): нет логирования безопасных метаданных (request_id, длительность, статус).
   Доказательство: В diff отсутствуют логи; CASE.md (стр. 70) и план (стр. 9) фиксируют требование OBS-1.
   Последствия: Снижение поддерживаемости и трассируемости; трудности в операционке.
   Критичность: Средняя.

7) Место: TRAINING_PR.diff app/api.py:30–31
   Проблема: Потенциально отсутствующая зависимость — импорт `app.dependencies.review_service` не подтверждён.
   Доказательство: Импорт есть в diff, сопутствующих изменений нет.
   Последствия: ImportError при интеграции, сбой приложения.
   Критичность: Средняя.

8) Место: TRAINING_PR.diff app/api.py:35–38; OpenAPI контракт
   Проблема: Нет явной схемы тела/ответа (Pydantic моделей/response_model), required `diff` не зафиксирован в OpenAPI.
   Доказательство: Сигнатура `create_review(payload: dict) -> dict[str, str]`; отсутствие моделей означает «свободный объект» в OpenAPI.
   Последствия: Размытый контракт, слабая валидация, сложнее генерировать клиенты.
   Критичность: Средняя.

9) Место: TRAINING_PR.diff app/review_service.py:19–21
   Проблема: Неограниченная длина prompt — весь diff встроен в запрос к LLM без чанкинга/обрезки.
   Доказательство: `prompt = f"...\n{diff}"` без фильтров.
   Последствия: Переполнение контекста модели, рост затрат/латентности.
   Критичность: Средняя.

10) Место: project_management.md:21 (Mermaid Gantt)
    Проблема: Потенциальная синтаксическая ошибка — двоеточие в названии задачи и двоеточие перед id: `LLM: безопасность и timeout :a3, ...`.
    Доказательство: Строка с двумя двоеточиями; Mermaid использует двоеточие для разделения имени и id.
    Последствия: Диаграмма может не отрендериться корректно; подрыв доверия к плану.
    Критичность: Средняя.

11) Место: project_management.md:34 (раздел «Как использовали AI»)
    Проблема: Заявление «корректность Mermaid Gantt» противоречит п. 10.
    Доказательство: «корректность Mermaid Gantt» указана как проверенная, но обнаружен риск синтаксиса.
    Последствия: Несогласованность документации; риск ложного ощущения готовности.
    Критичность: Низкая/Средняя.

12) Место: TRAINING_PR.diff app/review_service.py:19; app/api.py:36–37; CONTEXT.md «Что пока неизвестно»
    Проблема: Использование аннотаций `dict[str, str]` требует Python ≥3.9, целевая версия не зафиксирована.
    Доказательство: Аннотации в diff; CONTEXT.md указывает версию Python как открытый вопрос.
    Последствия: Риск несовместимости при деплое на Python <3.9.
    Критичность: Низкая/Средняя.
