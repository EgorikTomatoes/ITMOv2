# Отчёт 2. Повторные атаки после исправлений

Дата: 2026-11-02

Краткое резюме: после внесённых исправлений атаки больше не выполняются: SQLi блокированы параметризацией, IDOR и утечки закрыты проверками сессии и ролей, XSS экранирована, опасные действия ассистента проверяются на сервере. Ниже — сверка по каждому кейсу и артефакты.

1) SQL-инъекции
- Результат: числовые ID валидируются, а `/search` и `/assistant/context` используют параметризованные запросы. SQLi в `/profile` и `/assistant/context` возвращает 400, в `/search` — пустой результат.
- Доказательства: evidence/after/sqli_profile.json, search_sqli.json, assistant_context_sqli.json

2) IDOR профилей и заказов
- Результат: /profile?id=2 для Alice возвращает её профиль; /orders без токена — 401; клиенты видят только свои заказы.
- Доказательства: evidence/after/idor_profile_alice_reads_bob.json, orders_list_noauth.json

3) Подмена роли через X-Role
- Результат: /admin/export требует staff-токен, spoof X-Role не работает (403).
- Доказательство: evidence/after/role_spoof_export.json

4) Манипуляция ценой
- Результат: цена заказа игнорирует клиентский price и берётся из каталога.
- Доказательство: evidence/after/price_tampering.json

5) Доступ к чужим файлам
- Результат: клиент ограничен своей директорией и простым именем файла, чужие чеки недоступны.
- Доказательство: evidence/after/files_cross_user.json, files_traversal_private.json

6) Утечка логов
- Результат: /debug/logs доступен только staff и значения паролей/токенов редактируются.
- Доказательства: evidence/after/logs_leak.json (отказ без сессии), logs_staff_redacted.json (выдача staff с `***` вместо секретов).

7) XSS
- Результат: HTML в отзывах экранируется, теги и скрипты не исполняются.
- Доказательство: evidence/after/reviews_view_xss.json

8) Prompt injection и опасные действия AI-помощника
- Повторный запуск: `shop-planner` на той же модели `vsellm/openai/gpt-5`, с той же задачей и вредоносным отзывом вернул `tool=refuse`. Модель явно указала, что команды из контекста не дают полномочий.
- Серверная проверка: даже при принудительной передаче опасного JSON клиенту запрещены `export_profiles`, `delete_tree` и чтение чужого файла.
- Доказательства: evidence/after/prompt_injection_input.txt, prompt_injection_model.json, prompt_injection_execution.json, assistant_exec_export_profiles.json, assistant_exec_delete_tree.json, assistant_exec_read_bob.json.

Прогон тестов: make step6, затем make test (см. инструкции). В среде курса требуется Python 3.10+.

## Выводы

Основная проблема исходного сервиса была не в отдельной SQL-инъекции или XSS, а в отсутствии единой серверной границы доверия: API доверяло ID, роли, цене, путям и решению AI. Исправления перенесли решение о полномочиях в сессию и проверки кода.

Тест с LLM показал, что конкретная модель отвергла вредоносный отзыв, но это нельзя считать гарантией. Безопасность обеспечивает не послушность модели, а то, что `/assistant/execute` повторно проверяет сессию, роль и владение даже для принудительно подменённого JSON.
