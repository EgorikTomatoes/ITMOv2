# Рефлексия

Больше всего помогло заранее выбрать публичную границу проверки. Когда seam был
сформулирован как `tools/call`, тесты получились независимыми от внутреннего
устройства сервера: им всё равно, какими функциями разбираются аргументы, но они
ловят изменение MCP-контракта. RED → GREEN также дал честное подтверждение, что
новые тесты действительно способны упасть, а не проходят случайно.

Полезным оказалось разделение ролей подключений. `AGENTS.md` хранит постоянные
ограничения проекта, TDD-skill подсказывает способ разработки только для
подходящих задач, MCP предоставляет агенту доменную операцию, а hook собирает
все проверки в один автоматический ответ. Если сложить всё в один длинный prompt,
правила труднее переиспользовать и проще забыть.

Помешали две детали среды. Сначала правила лежали в `agents.md`, поэтому имя не
соответствовало механизму автоматического обнаружения; потребовалось вмешательство
и переименование в `AGENTS.md`. Кроме того, OpenCode пишет служебный лог вне
репозитория, поэтому проверка `opencode mcp list` потребовала явного разрешения на
доступ, хотя сам MCP работает локально.

Отдельно пришлось остановиться перед внешним агентским запуском через VseLLM:
он отправил бы содержимое локальных правил и skill провайдеру. Проблему удалось
решить без ослабления проверки: локальный Codex-агент прочитал правила и skill,
вызвал MCP через локальный stdio-клиент и получил оба результата. Это хороший
пример того, что полная автоматизация не отменяет решения человека о границе
передачи данных: требуемый workflow можно подтвердить, не отправляя проект ещё
одному внешнему сервису.

В следующий раз я бы сразу делал узкий MCP tool и отдельно сохранял машинный
транскрипт каждого важного запуска. Наличие файла конфигурации ещё ничего не
доказывает; полезнее короткие артефакты, где видны команда, exit code и реальный
ответ.
